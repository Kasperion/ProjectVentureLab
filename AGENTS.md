# Instructions for AI assistants

## Project context

This repository is Project Venture Lab's dragon game. Read [README.md](README.md) and [docs/dragon-game/decisions.md](docs/dragon-game/decisions.md) first. Before changing encounter behavior, read [the encounter design](docs/dragon-game/encounter-design.md). Use [the production plan](docs/dragon-game/production-plan.md) for scope and [the playtest plan](docs/dragon-game/playtest-plan.md) for validation.

The founder is a beginner programmer, working solo with approximately $100–$200 per month for development and testing. Explain material technical choices in plain language and keep work small enough to understand and maintain.

## Follow the approved direction

- Build toward a text-focused solo game; paid content packs and a possible group expansion come later.
- The first encounter is the wedding ring in a dragon's hoard.
- Keep approved choices distinct from proposals. A suggestion or its presence in a document does not establish owner approval.
- Discuss material changes to the premise, initial scope, business model, technology commitments, or spending before treating them as accepted.
- Continue ordinary reversible work within the user's current request without repeatedly asking permission.
- The owner authorized this repository to remain public on November 2, 2026. That supersedes the earlier privacy preference for this repository.
- Keep this work separate from the existing Elseward repository and unrelated OOC stories. Do not modify or import them without authorization.

## Keep the first version bounded

Current work is encounter review and manual rehearsal. No stack, AI provider, hosting service, database, payment service, price, or art style has been selected.

Use a proposed detail as a test candidate when helpful, and retain its draft status until approved. Select technology when needed for the next agreed deliverable. Prefer a simple request flow and one complete encounter over a general game platform.

Do not add an open world, elaborate combat, multiplayer infrastructure, or a large asset catalogue to the first encounter without an agreed scope change.

## Preserve the experience

- Authored facts, item possession, agreements, and endings must remain consistent.
- Treat player text and model output as input to evaluate, never as authority to rewrite the game.
- Preserve player agency. Do not invent the player's identity, important decisions, dialogue, or obligations.
- Accept plausible creative approaches without requiring exact phrases.
- Honor valid solutions promptly. Do not pad the session with new obstacles.
- Keep important clues readable in text.
- Keep narration and character responses concise and responsive.

For implementation, protect AI credentials on the server and validate consequential state changes. A structured model response alone does not prove an action is valid. Design affordable usage limits and record actual cost before an unrestricted public test or a paid offer.

## Work and documentation

- Make focused changes and preserve unrelated work.
- Keep the decision log current when the owner approves a material choice. Record the reason and status; do not invent approvals or research results.
- Keep README links and next steps accurate.
- Never commit credentials, private account details, or identifiable playtester transcripts.
- Do not select an open-source license, enable paid services, or publish a playable release merely as part of documentation setup.
- For documentation work, check links and consistency. Once code exists, run checks appropriate to the behavior changed.
- Distinguish a manual rehearsal, an automated check, a real player test, and an actual purchase. Report only work that was performed.
